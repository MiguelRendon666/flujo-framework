# 0.13.0 (propuesto) — Separar el stack real del core: `flujo-dotnet` + `flujo-node`

> Origen: instalación de flujo sobre un proyecto Tauri+Vue+TS reveló que el "core agnóstico" no lo era del todo — 4 de 7 archivos que la sesión tuvo que escribir a mano existían solo porque el template asumía .NET. Este documento es el diagnóstico completo (flujo-core + flujo-devexpress) y el diseño de la separación en 3 capas: **core (universal) → stack-pack de lenguaje/runtime → stack-pack de framework**.

## 1. Causa raíz

`flujo-devexpress` se planteó como el contenedor general ".NET/XAF" (ver decisión original), pero desde el día uno **nunca tuvo templates ni comandos** — es puramente una biblioteca de 23 skills de referencia DevExpress (Blazor/XAF/XPO). Todo lo que sí genera archivos concretos de proyecto (`gauntlet.json`, CI, `.editorconfig`, `settings.json`) vive en `flujo-core`, y se escribió una sola vez asumiendo dotnet porque el primer (y único) proyecto real donde se probó el framework era `ReporteriaGrupoMalia` (.NET/XAF). El framework nunca se volvió a auditar contra un segundo stack hasta ahora.

Conclusión: **no es un bug puntual de una instalación, es deuda de diseño del framework desde su origen.**

## 2. Buena noticia: el motor SÍ es agnóstico

Auditados los 11 scripts de `plugins/flujo-core/scripts/*.ps1` (el "engine" que corren los hooks): `gauntlet.ps1`, `style-check.ps1`, `spec-guard.ps1`, `readiness.ps1`, `stop-dod.ps1`, `tasks-complete.ps1`, `context-budget.ps1`, `block-bash.ps1`, `gherkin-check.ps1`. Ninguno tiene lógica hardcodeada de stack — todos leen `gauntlet.json`/`flujo.json` y ejecutan lo que ahí diga. **El problema es 100% de contenido de templates, no de motor** (con una excepción menor, ver §5).

## 3. Inventario — qué sale de `flujo-core` hacia `flujo-dotnet`

| Archivo en flujo-core hoy | Qué tiene de .NET quemado | Destino |
|---|---|---|
| `templates/gauntlet.json` | 8/11 etapas: `dotnet build/format/test/stryker` | Se mueve completo a `flujo-dotnet/templates/gauntlet.json` |
| `templates/stryker-config.json` | Schema entero es de Stryker**.NET** (`mutation-level`, etc.) — inválido para Stryker JS | Se mueve completo |
| `templates/ci/quality-gate.yml` | Pipeline entero: `setup-dotnet@v4`, `dotnet build/format/test` | Se mueve completo |
| `templates/.editorconfig` | Sección `[*.cs]` (`csharp_style_namespace_declarations`, `dotnet_diagnostic.IDE0005`) | Sale esa sección; la sección `[*]` (charset/crlf/trim) se queda en core, es universal |
| `templates/.claude/settings.json` | `permissions.allow`: `Bash(dotnet build*)`, `Bash(dotnet format*)`, `Bash(dotnet test*)` — **hallazgo nuevo, no lo habíamos visto antes** | Sale ese bloque; core deja `permissions.allow` vacío/mínimo |
| `commands/flujo-init.md` (paso 5) | Instrucción textual "verificar que los comandos del stack (`dotnet ...`)" — asume dotnet en la prosa del propio manual de instalación | Se reescribe agnóstico (ver §6) |
| `skills/gauntlet/SKILL.md` | Ejemplo `dotnet ...` en la tabla de etapas (cosmético, no ejecuta nada) | Genericizar el ejemplo |
| — (no existe) | **Gap, no hardcodeo**: no hay ningún template de config de test-runner JS (`vitest.config.ts`/`jest.config`) porque .NET no lo necesita (vive en el `.csproj`) | Nuevo template en `flujo-node` |

`dod.json`, `docs/ARCHITECTURE.md`, `CLAUDE.md` (placeholder `<completar>`), `flujo.json` (exemptPaths/exemptModes/exemptions) → **auditados y son genuinamente agnósticos**, no tienen nada que mover.

## 4. Qué sale de `flujo-devexpress` — el hallazgo que no esperabas

Las 23 skills `devexpress-xaf-*` / `devexpress-blazor-*` son **genuinamente específicas de DevExpress**, no de .NET genérico — se quedan donde están, ese plugin queda correcto tal cual para su función.

Pero hay una: **`skills/conexion-bases-datos/SKILL.md` no es XAF, ni siquiera es .NET.** Es infraestructura interna de Grupo Malia/Reyma: IPs privadas (`172.21.x/172.22.x/172.24.x`), nombres de sitios reales (Orangire, Recinto, Hotel Villaseca, Caffito, Krallar, Camino Viejo, Moksha), y la ruta exacta de un archivo de credenciales en tu máquina (`C:\Users\Pablninn18\.claude\mcp-servers\dbhub\dbhub.toml`). Esto:

- **No pertenece a `flujo-dotnet`** (no es de lenguaje/runtime).
- **No pertenece a ningún stack-pack compartible** — es topología de red y config de un cliente/negocio específico, no conocimiento técnico reutilizable.
- **Está commiteada en un repo con remote a GitHub** (`https://github.com/MiguelRendon666/flujo-framework.git`, referenciado además como marketplace fuente para quien instale el plugin). Si ese repo es público, o si algún día invitas colaboradores o lo forkeas, estás exponiendo topología de red interna de la empresa dentro de un plugin que se anuncia como "pack de stack DevExpress" reusable.

**Recomendación dura: sacar ese archivo del repo por completo.** Esa info (rutas locales, IPs internas, qué sitio usa qué motor) debe vivir en config local no versionada (`.claude/settings.local.json`, o un `CLAUDE.md`/nota privada fuera de git), nunca en un plugin de marketplace. Esto es independiente de la separación dotnet/node — es un problema de exposición, no de agnosticismo.

## 5. Bug de agnosticismo real en el motor (no es de stack-pack, hay que arreglarlo igual)

`spec-guard.ps1`, `mark-dirty.ps1` y `scan-comments.ps1` tienen la misma lista quemada en el propio script:
```
$codeExt = @('.cs', '.razor', '.css', '.scss', '.js', '.ts', '.sql', '.csproj', '.props', '.targets')
```
Ya mezcla extensiones .NET y JS a mano (no es que solo piense en dotnet), pero es una lista fija en el engine — le faltan `.vue`, `.jsx`, `.tsx`, `.py`, etc., y cualquier stack nuevo requiere tocar el motor, no solo instalar un pack. **Esto sí es responsabilidad de `flujo-core`:** debería salir de `flujo.json` (ej. `codeExtensions: [...]`, poblado por cada stack-pack al instalarse, con default mínimo en core) en vez de vivir hardcodeado en 3 scripts distintos.

## 6. `flujo-node` — el stack equivalente para JS/TS

Espejo 1:1 de lo que sale hacia `flujo-dotnet`:

| Archivo | Contenido propuesto |
|---|---|
| `templates/gauntlet.json` | `build`: `npm run build` · `format`: `npx prettier --check .` · `theme-check`/`gherkin`/`docdrift`: iguales (agnósticos, ya están en core) · `arch`: `npx dependency-cruiser --validate` (`enabled:false` por defecto, igual que hoy) · `unit`: `npx vitest run --coverage` · `integration`: `npx vitest run tests/integration` (`enabled:false` por defecto) · `bdd`: `npx cucumber-js` · `e2e`: `npx playwright test` (`enabled:false` por defecto) · `mutation`: `npx stryker run` |
| `templates/stryker-config.json` | Schema real de Stryker **JS** (`mutate`, `testRunner`, `packageManager`, `reporters`) — nada que ver con el schema .NET |
| `templates/vitest.config.ts` | Nuevo — hoy este hueco no existe en ningún lado, lo tuviste que inventar tú solo |
| `templates/ci/quality-gate.yml` | `actions/setup-node@v4`, `npm ci`, `npm run build`, `npx eslint .`, `npx vitest run --coverage` |
| `.editorconfig` (fragmento) | Sección `[*.{js,ts,vue,jsx,tsx}]`: indent 2, comillas, etc. |
| `.claude/settings.json` (fragmento) | `permissions.allow`: `Bash(npm run*)`, `Bash(npx eslint*)`, `Bash(npx vitest*)`, `Bash(npx tsc*)` |
| `CLAUDE.md` (snippet "Stack") | Plantilla pre-armada con las preguntas correctas para Node: framework, bundler, gestor de paquetes, convenciones |

Y, mirando el patrón `flujo-devexpress` (framework-specific sobre `flujo-dotnet`), el hueco natural a futuro es un **`flujo-vue`** (o `flujo-react`, `flujo-tauri`) que se instale ENCIMA de `flujo-node` y solo aporte skills de componentes — nunca vuelve a tocar `gauntlet.json`/CI/editorconfig, porque de eso ya se encargó `flujo-node`.

## 7. Arquitectura de 3 capas (cómo se integran)

```
flujo-core (universal, motor + docs + DoD)
   └── flujo-dotnet (lenguaje/runtime: gauntlet, CI, editorconfig, settings, stryker .NET)
   │       └── flujo-devexpress (framework: skills XAF/Blazor — SIN conexion-bases-datos)
   └── flujo-node (lenguaje/runtime: gauntlet, CI, editorconfig, settings, stryker JS, vitest)
           └── flujo-vue / flujo-react / flujo-tauri (futuro, framework: skills de componentes)
```

Regla de instalación: **un proyecto instala `flujo-core` + exactamente un pack de lenguaje (`flujo-dotnet` o `flujo-node`) + opcionalmente un pack de framework** que declare depender del de lenguaje correspondiente (documentado en su `README.md`, el marketplace de Claude Code no tiene campo formal de `depends`).

### Cambios concretos en `/flujo-init` (paso 5)

Hoy dice (textual): *"gauntlet.json: verificar que los comandos del stack (`dotnet ...`) apuntan a proyectos reales..."* — se reescribe a:

1. Detectar qué stack-pack de lenguaje está en `enabledPlugins` (`.claude/settings.json` del proyecto o del usuario): `flujo-dotnet@flujo`, `flujo-node@flujo`, etc.
2. Si hay exactamente uno instalado → copiar `gauntlet.json`, `ci/quality-gate.yml`, el fragmento de `.editorconfig` y el fragmento de `permissions.allow` **desde `${stack-pack}/templates/`**, no desde `flujo-core/templates/`.
3. Si hay más de uno (monorepo) → avisar y pedir confirmación de cuál aplica a cuál carpeta, o generar ambos si el usuario lo confirma.
4. Si no hay ninguno instalado → generar el `gauntlet.json` **mínimo agnóstico** (solo las 3 etapas universales: `theme-check`, `gherkin`, `docdrift`) y avisar explícitamente: *"no hay stack-pack instalado, faltan las etapas build/format/unit/etc. Instala `flujo-dotnet` o `flujo-node`, o complétalas a mano."* — nunca rellenar `dotnet` por default silenciosamente, que es lo que pasaba hasta hoy.

`flujo-core` deja de traer `gauntlet.json` con comandos, `ci/quality-gate.yml`, `stryker-config.json`, y la sección `[*.cs]` de `.editorconfig`. Se queda solo con lo universal: docs/, specs/, `dod.json`, `flujo.json`, `.editorconfig` raíz, `CLAUDE.md` esqueleto.

### `marketplace.json` — cambios de registro

Agregar dos entradas nuevas junto a `flujo-core`/`flujo-devexpress`:
```json
{ "name": "flujo-dotnet", "source": "./plugins/flujo-dotnet", "category": "stack-lang" },
{ "name": "flujo-node",   "source": "./plugins/flujo-node",   "category": "stack-lang" }
```
Y en `flujo-devexpress/.claude-plugin/plugin.json` documentar en `description`/README que ahora requiere `flujo-dotnet` instalado (antes era autocontenido porque cargaba con el peso de generar templates .NET él solo — ya no).

## 8. Acción inmediata en tu proyecto Tauri/Vue

Confirmado: desinstalar `flujo-devexpress` de ese proyecto es correcto. Las 23 skills son 100% DevExpress/XAF/Blazor — cero superposición con Tauri+Vue+TS — y además cargaba de rebote la skill de infraestructura interna de Grupo Malia (`conexion-bases-datos`) que no debería estar expuesta ahí de todas formas.

## 9.5. ¿Los 11 pasos del gauntlet aplican igual sin importar el stack?

Pregunta disparada por la instalación real: de los "4 de 11" que el agente instalador apagó (`format`, `arch`, `integration`, `e2e`), **3 ya venían `enabled:false` en el template incluso en su versión .NET actual** — no es una discriminación contra Node, es un default universal ya presente hoy. Auditando etapa por etapa, con equivalente real en el ecosistema JS para cada una:

| # | Etapa | ¿Concepto universal? | Tool .NET | Tool Node/JS equivalente | Default hoy | ¿Correcto mantenerlo así en ambos stacks? |
|---|---|---|---|---|---|---|
| 1 | `build` | Sí | `dotnet build -warnaserror` | `vue-tsc --noEmit` / `tsc --noEmit --strict` (o `npm run build` si el bundler falla con errores TS) | ON | Sí — compilar/tipar sin warnings no requiere infra extra en ningún stack, debe ir siempre encendido |
| 2 | `format` | Sí | `dotnet format --verify-no-changes` | `npx prettier --check .` | ON en template, pero **la sesión lo apagó porque no había prettier/eslint instalado** | **Asimetría real, no bias:** `dotnet format` viene incluido gratis en el SDK de .NET desde el día uno; en JS el formatter es una decisión de tooling que el proyecto tiene que instalar. No es que el paso "no aplique" a JS — es que .NET no requiere setup y JS sí. Ver propuesta abajo. |
| 3 | `theme-check` | Sí (ya agnóstico) | — (script interno, CSS/SCSS) | igual | Gated por switch | Sin cambios, ya funciona igual en cualquier stack con CSS |
| 4 | `gherkin` | Sí (ya agnóstico) | — (script interno, `.feature`) | igual | ON | Sin cambios |
| 5 | `arch` | Sí | `dotnet test tests/Arch` (NetArchTest/ArchUnitNET) | `npx dependency-cruiser --validate` / `eslint-plugin-boundaries` | **OFF ya en el template .NET** | Correcto dejarlo off en ambos — definir reglas de arquitectura (qué capa puede depender de cuál) es una decisión de equipo, no algo que flujo pueda asumir ni en .NET ni en JS. No es bias de stack. |
| 6 | `unit` | Sí | `dotnet test ${testProject} /p:CollectCoverage=true` | `npx vitest run --coverage` | ON (gated por `testing.enabled`) | Sí en ambos. Nota técnica: el placeholder `${testProject}` asume "ruta a un proyecto" (concepto .NET); Vitest no necesita esa sustitución porque descubre tests por convención — `flujo-node` puede simplemente no usar el placeholder. |
| 7 | `integration` | Sí | `dotnet test tests/Integration` | `npx vitest run tests/integration` (con harness de API/DB real) | **OFF ya en el template .NET** | Correcto dejarlo off en ambos — exige infra de pruebas real (DB de prueba, API levantada), mismo costo de montaje en los dos stacks. |
| 8 | `bdd` | Sí | `dotnet test --filter Category=bdd` (Reqnroll/SpecFlow) | `npx cucumber-js` | Gated por `testing.bdd` | Sí, mapea perfecto — `gherkin-gen` ya genera `.feature` agnósticos, Cucumber.js los consume igual que Reqnroll. |
| 9 | `e2e` | Sí | `dotnet test tests/E2E` (Playwright.NET/Selenium) | `npx playwright test` | **OFF ya en el template .NET** | Correcto dejarlo off en ambos — requiere la app corriendo + navegador, mismo costo en los dos stacks. |
| 10 | `mutation` | Sí | `dotnet stryker` | `npx stryker run` | ON (gated por `testing.enabled`) | Sí — Stryker es *nativamente* multi-lenguaje (StrykerJS es tan maduro como Stryker.NET, de hecho es el original). No hay motivo para tratarlo distinto. |
| 11 | `docdrift` | Sí (ya agnóstico) | `echo docs-rewrite --check` | igual | **OFF**, y además... | **Hallazgo aparte, de core, no de stack:** el `cmd` de esta etapa es literalmente `echo docs-rewrite --check` — un `echo` nunca falla, así que aunque se encienda, esta etapa **nunca puede fallar de verdad**. No está conectada a nada real (no hay `docdrift-check.ps1` como sí existe para `theme-check`/`gherkin`). Es una etapa decorativa hoy, en cualquier stack. Debería pasar a `"internal": "docdrift-check"` invocando de verdad al skill `docs-rewrite --check`. |

### Conclusión de esta sección

**El concepto de las 11 etapas es 100% universal — ninguna es intrínsecamente ".NET-only".** Lo que pasó en tu instalación no fue el plugin discriminando contra Node: `arch`/`integration`/`e2e` vienen off por defecto **en cualquier stack** porque exigen infraestructura de pruebas que ningún template puede asumir sin preguntar. El único caso con asimetría real es `format`, y no es conceptual — es que `dotnet format` es gratis (viene en el SDK) y un formatter JS es una decisión de tooling que alguien tiene que tomar primero.

### Propuesta para el design

1. **`arch` / `integration` / `e2e` quedan `enabled:false` por default en AMBOS stack-packs** (ya es así) — pero en vez del `avisarlo` pasivo actual, `/flujo-init` debería **ofrecer explícitamente** encenderlas con un starter mínimo (igual que ya hace con `testing.bdd`, que sí explica trade-offs antes de preguntar): *"¿Quieres que arme un `tests/Arch` con ArchUnitNET / un `dependency-cruiser.config.js` con reglas base? Esto activa la etapa `arch` como bloqueo duro."* Mismo trato para `integration` y `e2e` en los dos stacks — ahora mismo la skill de `/flujo-init` solo pregunta por `testing.bdd` con esa profundidad; las otras 3 etapas se resuelven en silencio.
2. **`format` deja de ser "todo o nada".** En `flujo-node`, si `/flujo-init` no encuentra config de prettier/eslint, en vez de apagar la etapa directo debe ofrecer escribir un `.prettierrc` mínimo (default sano de la industria) y dejarla encendida — solo apagarla si el usuario rechaza explícitamente instalar un formatter. Mismo patrón de "preguntar antes de apagar en silencio" que ya usa el framework para `style.enabled`/`testing.project`.
3. **`unit` en `flujo-node` no necesita el mecanismo `${testProject}`** — Vitest descubre tests por convención; el placeholder queda como opción del stack-pack, no como requisito del motor (`gauntlet.ps1` ya solo hace el reemplazo si el string lo contiene, así que es compatible sin tocar el engine).
4. **`docdrift` se arregla en `flujo-core` (no es de stack)**: pasar de `cmd: echo ...` a `internal: docdrift-check`, con un script real que invoque `docs-rewrite --check`. Aplica igual a `flujo-dotnet` y `flujo-node` porque ya vive en las 3 etapas universales del core.

## 9. Resumen ejecutivo

| Pregunta | Respuesta |
|---|---|
| ¿El motor de flujo es agnóstico? | Sí, los 9 scripts del engine no tienen lógica de stack — confirmado por auditoría. |
| ¿Los templates son agnósticos? | No — 5 archivos de `flujo-core` tenían .NET quemado: `gauntlet.json`, `stryker-config.json`, `ci/quality-gate.yml`, sección `[*.cs]` de `.editorconfig`, permisos `dotnet *` en `settings.json`. |
| ¿`flujo-devexpress` tiene contenido .NET genérico que debería ser de `flujo-dotnet`? | No — sus 23 skills son legítimamente XAF/Blazor. Sí tiene una skill que no es ni XAF ni .NET: infraestructura privada de la empresa, que debe salir del repo por completo. |
| ¿Qué falta para `flujo-node`? | Un plugin nuevo, espejo de `flujo-dotnet`, con `gauntlet.json`/CI/`.editorconfig`/`settings`/`stryker-config`/`vitest.config.ts` propios de Node — hoy no existe nada de esto. |
| ¿Cómo se integran sin romper el core? | 3 capas: core (universal) → stack-pack de lenguaje (dotnet/node) → stack-pack de framework (devexpress/vue futuro). `/flujo-init` detecta el pack de lenguaje instalado y copia SUS templates en vez de asumir dotnet. |
