# 0.10.0 — Pilar Theme-first / Gobernanza de estilos (diseno en construccion)

> Documento vivo. El framework es global/agnostico: la POLITICA vive en el core; la DETECCION concreta y la fuente del tema viven en el proyecto o en un stack-pack. Tecnologia solo como ejemplo etiquetado.

## Objetivo real (NO es "cero valores quemados" a secas)
El fin no es solo prohibir valores quemados: es un **sistema de diseno COHERENTE** — pocos tokens, bien nombrados, reutilizados. Una "sopa de tokens" (`--card-radius: 2rem`, `--popup-radius: 2.2rem`) es tan mala o peor que valores quemados.

## Consolidacion de tokens (la preocupacion central del usuario)
Antes de crear un token nuevo:
1. **Buscar en el inventario de tokens** (el/los archivo(s) de tema; ubicacion definida por el usuario) si ya existe uno con: el mismo valor, un valor casi-igual (dentro de una tolerancia), o el mismo rol semantico.
2. Match exacto o de rol -> **reusar**, no crear.
3. **Casi-duplicado** (mismo rol, valor ligeramente distinto: 2rem vs 2.2rem) -> **PARAR y PREGUNTAR**: "¿intencional o inconsistencia? ¿reuso `--radius-card` o creo uno nuevo?". Nunca auto-crear el casi-duplicado (puede ser una inconsistencia vieja de IA que hay que consolidar; lo decide el usuario).
4. **Naming semantico/escala, NO por componente:** preferir `--radius-md` (reutilizable) sobre `--radius-card`/`--radius-popup` (fomentan duplicacion).
5. Mismo valor reaparece para otro objeto -> proponer **renombrar el token a algo generico y reutilizarlo**, no crear un segundo.

## Decisiones cerradas
- Nivel 3: **theme-first estricto, bloqueo duro** ante valores quemados de identidad visual.
- **Pilar aparte de `design-critic`** (que es juicio cualitativo de UI/UX); theme-first es gate estructural. Complementarios.
- Mecanismo: **etapa de guantelete deterministica** (opcion B) para el bloqueo + un **skill** para generar/refactorizar + consolidar tokens.
- **Fuente del tema = definida por el usuario** (igual que la ubicacion del proyecto de pruebas), no una ruta fija.
- **Activacion = eleccion de instalacion** (no todo proyecto tiene UI); con explicacion. Activo = no-negociable.

## Gates de NO-aplicabilidad (cuando NO dispara)
- **Cambios que no tocan estilos** (mover/reordenar elementos) -> es dominio de `design-critic` (correccion UI/UX), NO de theme-guard.
- **Estilos de framework/vendor que el usuario NO controla** (ejemplo: el estilo propio de un framework de UF como XAF) -> **exento y no-negociable**: no se juzga ni se bloquea lo que el usuario no define. Solo aplica a estilos AUTORADOS por el usuario.

## Exenciones de valor (propuesta, a confirmar)
Permitidos sin tema (estructurales/universales, sin identidad visual):
- `0` (y `0px`/`0%`/`0rem`).
- Porcentajes (`100%`, `50%`).
- Unidades de viewport (`100vh`/`100vw`) y fracciones de grid (`1fr`).
- Palabras clave (`auto`, `none`, `inherit`, `initial`, `unset`, `transparent`, `currentColor`).
- DEBATIBLE: `1px` (hairline). El usuario inclina a que SI deba ser tema.

NUNCA exentos (identidad visual -> deben venir del tema): colores (hex/rgb/hsl/nombre), gradientes, sombras, radios > 0, tamanos/familias/pesos de fuente, espaciados > 0, duraciones/timing, z-index (escala), breakpoints.

## Determinismo exacto (la frontera)
Regla: cualquier **literal de identidad visual** (color, gradiente, sombra, radio>0, fuente, espaciado>0, duracion, z-index, breakpoint) que NO este en la lista de exenciones se considera **valor quemado -> bloqueo duro**. La lista de exenciones define el limite; todo lo demas de identidad visual, quemado.

## Agnosticismo y stack-packs (estrategia FrameworkHelping)
- El core (flujo-core) define POLITICA: cero quemados de identidad, theme-first, consolidacion de tokens, pregunta ante casi-duplicado.
- La DETECCION concreta vive por universo:
  - **Web** (Tauri/Electron/Vue/Angular/HTML puro) = mismo universo CSS -> un solo pack (ej. futuro `flujo-web`).
  - **.NET/Blazor, Flutter, Android, iOS** = cada uno su universo -> su propio pack (ej. `flujo-devexpress` ya existe; puede crecer con el enforcement Blazor incluidos los caminos raros C#<->JS<->CSS).
- Idea del usuario (aprobada como direccion): extensiones propias ("FrameworkHelping") que reducen el agnosticismo con herramientas nuestras por stack. Consistente con la distribucion hibrida ya decidida (core agnostico + stack-packs).
