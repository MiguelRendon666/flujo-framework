# 0.12.0 — Bootstrap / Greenfield (crear un proyecto desde cero con flujo)

> Cierra el gap: hoy flujo se INSTALA sobre un proyecto existente; esto lo crea DESDE CERO con gobernanza desde el dia uno. Probable ultima beta antes de 1.0.
> Patron de siempre: el core ORQUESTA (agnostico); el stack-pack SCAFFOLDEA el esqueleto concreto (o se delega a la herramienta nativa). El core no sabe crear un proyecto .NET vs Node vs Flutter — eso es especifico de cada universo.

## Flujo propuesto (`/flujo-new <nombre>`)
1. **PLANEAR primero:** constitution (principios), stack elegido por el usuario, arquitectura (via `brainstorming` + `arch`). El core NO asume el stack.
2. **SCAFFOLD del esqueleto:**
   - Si hay un **stack-pack con receta** -> usarla.
   - Si no -> el core **GUIA** al usuario a correr el scaffolder nativo (`dotnet new`, `npm create`, etc.) y wirea alrededor. El core no ejecuta creacion stack-especifica a ciegas.
3. **WIRE de gobernanza:** correr `flujo-init` sobre la estructura recien creada -> `requirePaths` / `testing.project` / `themeSource` quedan POBLADOS (porque los acabamos de crear), no vacios.
4. **PRIMERA spec/plan (opcional):** arrancar la primer feature con `/workflow-plan`.

## Que crea el CORE (agnostico, universal)
`git init` si no es repo; `.gitignore`; `README` skeleton; `docs/` (Diataxis + `constitution.md`); `specs/`; `flujo.json`/`gauntlet.json`/`dod.json`; `.editorconfig`; CI skeleton; `.claude/` hooks. **NO** el build/solucion/proyecto-de-pruebas stack-especifico.

## Que hace el STACK-PACK / herramienta nativa
El esqueleto concreto: solucion/estructura, proyecto de pruebas real, archivo de tema (si hay UI), build. Receta por universo (web, .NET, Flutter, mobile...).

## Conexion con el "verde real"
Un greenfield limpio (sin el feed privado ni las vulnerabilidades NuGet de Malia) es la mejor forma de lograr por fin el ciclo `plan -> scaffold -> implement -> pruebas -> DoD` TODO en verde. Bootstrap + verde real = el mismo tiro.
